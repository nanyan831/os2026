# Lab 1 交互提示词汇总

## 一、从实验目标到能够运行的内核

### 第 1 轮：先弄清楚实验要求

**问题：**

> 我们准备做 Lab 1，指导书在 http://8.135.34.58/lab2026/_book/，起始代码已经放在项目中。请先说明两项练习分别要解决什么问题，以及应该从哪些文件看起。先分析这一阶段，再根据结果决定下一步。

**解释：**

Lab 1 的重点是理解最小内核如何启动，并通过调试验证。练习一分析入口汇编中建立栈和进入 C 函数的操作；练习二观察从复位代码、OpenSBI 到内核入口的执行过程。先看 `kern/init/entry.S`、`kern/init/init.c` 和 `tools/kernel.ld`，再联系 Makefile 与输出接口。

**验证依据与下一步：**

初期工程按指导书建立在 `labcodes/lab1`；统一交付后代码位于 `code/`。下一步先解释入口汇编的两条指令，而不是直接扩展尚未要求的内核功能。

### 第 2 轮：为什么进入 C 之前要设置栈？

**问题：**

> `entry.S` 第一条是 `la sp, bootstacktop`。这里取的是地址还是内存中的值？为什么不能直接进入 C 函数？请结合栈定义解释，并告诉我应该检查哪些宏。

**解释：**

`la` 将符号地址装入寄存器，`sp` 是栈指针。这一行把 `bootstacktop` 的地址设为内核初始栈顶。C 函数调用可能保存寄存器、返回地址或局部变量，因此必须先有可用的栈。

`bootstack` 在 `.data` 中通过 `.space KSTACKSIZE` 静态预留空间。`KSTACKPAGE=2`，`PGSIZE=4096`，所以栈大小为 8192 字节。栈向低地址增长，初始 SP 应放在高地址边界 `bootstacktop`。

**验证依据与下一步：**

依据 `entry.S`、`kern/mm/memlayout.h` 和 `kern/mm/mmu.h` 核对大小与位置。还要通过 GDB 比较执行前后的 SP。随后追问第二条 `tail` 如何进入 C。

### 第 3 轮：`tail` 为什么不是普通函数调用？

**问题：**

> 建立栈后，代码执行 `tail kern_init`。它与 `call` 有什么不同？`kern_init` 为什么声明为 `noreturn`？请解释它是否需要返回到汇编入口。

**解释：**

`tail` 把控制权转交给 `kern_init`，不会像普通 `call` 一样建立返回到当前入口的新返回地址。本次反汇编中它成为跳转指令。`kern_init` 末尾是无限循环，不会返回，所以使用尾跳转符合其执行逻辑。

`noreturn` 是向编译器声明“不返回”的属性，真正保证不返回的是函数的执行逻辑，属性本身不会自动生成循环。

**验证依据与下一步：**

对照 `entry.S` 与 `init.c`，后续在 GDB 中观察 PC 是否进入 `kern_init`。下一步需要弄清这些符号的地址由谁决定。

### 第 4 轮：内核入口地址和镜像是怎么确定的？

**问题：**

> 指导书使用 `0x80200000` 作为内核入口，这个地址在哪里设置？Makefile 为什么同时生成 `bin/kernel` 和 `bin/ucore.img`？请把编译、链接与装载区分开。

**解释：**

`tools/kernel.ld` 设置基地址和入口符号，并安排代码、只读数据、可写数据等段。`ENTRY(kern_entry)` 设置 ELF 入口信息，实际指令位置还要结合段布局验证。

编译和汇编先生成目标文件，链接器按脚本生成带符号的 ELF 文件 `bin/kernel`；`objcopy` 再生成裸镜像 `bin/ucore.img`。GDB 使用 ELF 符号，QEMU 使用镜像启动。裸镜像没有 ELF 头，装载地址由外部配置决定。

**验证依据与下一步：**

用符号表或 ELF 信息核对 `kern_entry`，不能只根据文件名推断。然后实际在 Ubuntu 编译，看工具链是否可用。

### 第 5 轮：怎样判断编译成功？

**问题：**

> 现在请在 Ubuntu 中实际编译，列出使用的工具以及生成的文件。编译成功能否直接说明内核启动成功？如果失败，请先解释真实错误，再做必要修改。

**解释：**

进入 `code/` 执行 `make`，确认使用 RISC-V 交叉编译器，观察编译、链接与 `objcopy` 是否完成。应生成 `bin/kernel`、`bin/ucore.img`，以及反汇编和符号表等文件。编译通过只证明构建成功，还要实际启动 QEMU。

**验证依据与下一步：**

本工程在 Ubuntu 中实际编译通过。相应输出见[实验报告](report.md)。下一步运行 `make qemu`，观察是否出现内核字符串。

### 第 6 轮：为什么只看到 OpenSBI，没有内核输出？

**问题：**

> 原启动命令使用 `-device loader,file=...,addr=0x80200000`，但运行后只有 OpenSBI 信息，没有内核字符串。这能说明入口汇编有问题吗？应先看哪些启动信息，再决定改哪里？

**解释：**

先区分固件启动与内核启动。查看 OpenSBI 的 `Domain0 Next Address` 和 `Next Mode`，再确认镜像路径及 QEMU 参数。实际记录中，原命令的下一阶段地址为 `0x0`，不能据此直接归因于 `la` 或 `tail`。

本机改用 `-kernel bin/ucore.img` 后，固件显示下一阶段地址为 `0x80200000`，随后出现 `(THU.CST) os is loading ...`。调整的是启动参数，内核核心逻辑仍沿用起始代码。

**验证依据与下一步：**

依据固件输出和内核字符串确认修改生效。字符串之后持续运行符合 `kern_init` 的循环设计。接下来用 GDB 证明控制权确实经过预期入口。

## 二、用 GDB 验证前面的解释

### 第 7 轮：怎样连接调试器？

**问题：**

> 我们需要从第一条指令开始调试，但本机只有 `gdb-multiarch`。如何使用两个终端连接 QEMU？`-s` 和 `-S` 分别有什么作用？

**解释：**

两个 Ubuntu 终端均进入 `code/`，先执行 `make debug`，再执行 `make gdb`。`-S` 让虚拟 CPU 暂停，`-s` 开启默认 1234 端口的 GDB 服务。Makefile 在缺少专用 RISC-V GDB 时回退到 `gdb-multiarch`；调试器加载的是 `bin/kernel` 的符号。

**验证依据与下一步：**

实际已能连接远程目标。连接后先查看 `$pc` 和附近指令，再确定初始地址属于哪一阶段。

### 第 8 轮：初始 PC 为何是 `0x1000`？

**问题：**

> GDB 显示初始 PC 为 `0x1000`，它是不是 OpenSBI 的入口？请解释这一段指令如何把控制权交给固件，并给出验证命令。

**解释：**

本次 QEMU `virt` 配置下，`0x1000` 是复位 ROM，OpenSBI 位于 `0x80000000`。复位指令准备 hart ID、设备树等启动参数，从附近数据区取出固件入口后跳转。

```gdb
p/x $pc
x/6i $pc
x/2gx 0x1018
b *0x80000000
c
```

**验证依据与下一步：**

实际在 `0x80000000` 断点停住，证明完成了这次跳转。`0x1018` 附近是数据，应按数据查看。下一步观察固件何时进入内核。

### 第 9 轮：如何证明栈设置和 C 入口正确？

**问题：**

> 现在怎样验证 OpenSBI 进入了 `kern_entry`？如何证明 `la` 真正改变了 SP，而不只是重复解释源码？请给出能逐步观察的 GDB 操作。

**解释：**

先在内核入口停住，再核对栈顶符号和机器指令。本次 `la` 展开为两条指令，因此单步两次之后再比较 SP。

```gdb
b *0x80200000
c
info registers pc sp a0 a1
p/x &bootstacktop
x/3i $pc
si
si
info registers pc sp
b kern_init
c
```

**验证依据与下一步：**

本次设置后 `sp=0x80203000`，等于 `bootstacktop`；继续执行后到达 `kern_init=0x8020000a`。这些是当前构建的结果，不是所有环境中的固定符号地址。随后检查 C 初始化的实际行为。

### 第 10 轮：BSS 清零是否真的处理了非空区域？

**问题：**

> `kern_init` 中有 `memset(edata, 0, end - edata)`。`edata` 和 `end` 在哪里定义？如果它们相等，是否说明出错？报告中应如何描述？

**解释：**

两个符号由链接脚本提供，C 中用 `extern` 声明它们的地址。语句的通用目的是初始化零填充区域。当前构建中，两者都为 `0x80203008`，所以长度实际为 0；这与当前没有非空 BSS 区域一致。

**验证依据与下一步：**

对照链接脚本、符号表或 GDB 地址观察记录结果，不能写成“已经观察到非空 BSS 被清零”。接下来追踪内核字符串如何输出。

### 第 11 轮：没有完整设备驱动，字符如何显示？

**问题：**

> `cprintf` 最后是如何把字符送到终端的？请沿源码解释调用链，并说明这里的 `ecall` 与普通用户程序的系统调用有什么区别。

**解释：**

输出经过 `cprintf → vcprintf → vprintfmt → cputch → cons_putc → sbi_console_putchar → sbi_call → ecall`。本工程使用 legacy SBI：`a7` 放服务号，`a0` 等寄存器放参数，字符输出的服务号为 1。

这里由 S 模式内核请求 M 模式 OpenSBI 的服务，并非 U 模式应用向操作系统发起的系统调用。固件交接后仍能提供相应服务。

**验证依据与下一步：**

依次查看 `kern/libs/stdio.c`、`kern/driver/console.c` 和 `libs/sbi.c`，把真实输出与调用链对应起来。再检查指导书中的装载观察方式是否适合本环境。

### 第 12 轮：为什么 watch 没有抓到装载？

**问题：**

> 指导书建议用 `watch *0x80200000` 观察内核装载，但采用 `-kernel` 后没有看到对应写入。这是否代表镜像未装载？怎样用现有工具说明实际情况？

**解释：**

本环境中，QEMU 在 CPU 开始执行前已经装载镜像。GDB 连接时 PC 尚在 `0x1000`，但已经能从 `0x80200000` 反汇编出入口指令。之后的 watch 无法捕捉此前发生的装载。

**验证依据与下一步：**

用复位时的目标地址内容说明镜像已经存在，再用入口执行断点证明 CPU 到达了该处。下一步把这些源码解释和实际证据写入报告。
